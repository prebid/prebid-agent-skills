## Methodology notes

- **Why vungle is canary 5 (the F3 sample)**: ADR-007 documents 4 "F-class" fidelity patterns (F1/F2/F3/F4); vungle is the spec-blessed master sample for F3 (Site → App synthesis). The Go-side `VungleBidder` synthesizes an App context from Site + the `imp.ext.vungle.appStoreId` field BEFORE dispatch; upstream Java does the same. The SKILL template originally emitted neither. F-new-86 is the master-sample finding that retires this gap.
- **The vungle triple (F-new-86 + F-new-91 + F-new-92)**: the three patterns are coupled — F3 synthesis populates the App context, F-new-91 (three-key wrapper repack) restructures `imp.ext` into the `{prebid, bidder, vungle}` shape, F-new-92 (buyer-UID promotion) extracts `user.buyerUid` into `imp.ext.vungle.bid_token`. All three are runtime-mutation patterns and all three landed together in F2 Tier 3 step 3 (`d391e98`) as TODO scaffolds at the correct emit sites.
- **`BidderUtil.isResponseStatusCodeNoContent` and `checkResponseStatusCode` are phantom APIs**: F-new-90 surfaced this — the template was emitting calls to upstream-Java helper methods that **do not exist** in the upstream `BidderUtil` class. The Go side's `canonical-go-helpers` pattern was translated to non-existent Java method names. F2 Tier 1 retired this by dropping the calls when `ctx.http_status_kind == "canonical-helpers"` — Java framework handles 204/non-200 before makeBids is invoked. Was the vungle-unique Gate 1 blocker.
- **Cross-canary signal**: vungle's `constant-video` finding (F-new-64 canary 5 subagent ID, not yet retired) is the corpus' first surface of Rule 26 hardcoded-fallback beyond `constant-banner`. Other adapters with hardcoded video/audio/native fallback will hit this until the template generalizes the `constant-*` enum.
