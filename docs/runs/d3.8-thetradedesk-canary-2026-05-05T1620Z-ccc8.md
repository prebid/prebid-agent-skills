## Findings

### Validated: F-new-2 — template-macro endpoint TODO stub (HIGH; 2/16 corpus est.)

**Phase 2 status**: WORKED AS PREDICTED. ✓

This is the SECOND canary to confirm the multi-token-substitution / template-macro template gap (adverxo v5 was first). Spec encodes `endpoint_resolution.kind=template-macro` for thetradedesk; the template's `resolveEndpoint` enum supports only `static` + `dev-prod-toggle`; everything else (including `template-macro`, `multi-token-substitution`, `single-token-substitution`, `query-parameter-augmentation`) emits a TODO comment + returns `a.endpoint` unmodified:

```go
func (a *adapter) resolveEndpoint(request *openrtb2.BidRequest) string {
    // TODO[port-java2go]: endpoint_resolution_kind=multi-token-substitution
    // requires per-bidder customization (Rule 11/12/14).
    return a.endpoint
}
```

**Functional consequence**: Emitted Go does NOT substitute `{{.SupplyId}}` token. Upstream Go thetradedesk.go uses:
1. `text/template` parsed in Builder (line 220).
2. Pre-resolved `defaultEndpoint` via `macros.ResolveMacros(template, EndpointTemplateParams{SupplyId: config.ExtraAdapterInfo})` (line 226).
3. Per-request `buildEndpointURL(supplySourceId)` (lines 105-121) — falls back to defaultEndpoint when supplySourceId is empty; otherwise re-resolves with the per-request SupplyId.

Operator hand-fill required for production fidelity. The canary worked because `TEST_ENDPOINT = "https://test.example.com/bid"` has no `{{.SupplyId}}` placeholder (no token substitution observable).

**Captured**: in port-report.json::human_todos[]. Operator must:
1. Add `bidderEndpointTemplate string` + `defaultEndpoint string` + `templateEndpoint *template.Template` fields to `adapter` struct.
2. Parse config.Endpoint via `template.New(...).Parse(...)` in Builder.
3. Pre-resolve default using `macros.ResolveMacros(template, EndpointTemplateParams{SupplyId: config.ExtraAdapterInfo})`.
4. Add ExtraAdapterInfo regex validation (lines 213-218 upstream).
5. Replace `a.resolveEndpoint(request)` with `a.buildEndpointURL(supplySourceId)` per-imp.

**Severity**: HIGH. Both adverxo + thetradedesk now confirmed. Phase 3 should land the multi-token branch with `ctx.endpoint_token_set` schema (per canary v5 recommendation #1).

**Affected pairs in 5-pair MVP batch**: adverxo + thetradedesk (= 2/5).
**Affected pairs in full corpus**: adverxo + thetradedesk + aax (query-parameter-augmentation; related concern) + any other multi-token adapter. Conservative estimate 3-4 in corpus.

### NEW: F-new-31 — Rule 35 inverse typed-extra-info struct emission (HIGH; 2-3/16 corpus est.)

**Symptom**: Template's `{% if ctx.has_extra_info %}` branch emits an `extraInfo struct {...}` with TODO body and zero fields:

```go
type extraInfo struct {
    // TODO[port-java2go]: operator fills fields from the Java typed-config
    // subclass per Rule 35 inverse. Each Java field becomes a Go field with
    // `json:"X"` tag matching the upstream YAML key.
}
```

The empty struct doesn't compile (well, it compiles but is useless because `json.Unmarshal` into an empty struct silently drops all fields). Worse, the template doesn't emit any actual ExtraAdapterInfo handling beyond an empty `Unmarshal` call:

```go
func Builder(_ openrtb_ext.BidderName, cfg config.Adapter, _ config.Server) (adapters.Bidder, error) {
    a := &adapter{endpoint: cfg.Endpoint}
    if cfg.ExtraAdapterInfo != "" {
        if err := json.Unmarshal([]byte(cfg.ExtraAdapterInfo), &a.extraInfo); err != nil {
            return nil, fmt.Errorf("invalid extra info: %w", err)
        }
    }
    return a, nil
}
```

Upstream Go thetradedesk.go uses ExtraAdapterInfo as a STRING (NOT a JSON-encoded subclass). It validates via regex `([a-z]+)$` and uses it as the SupplyId for default endpoint precomputation. The template's Rule 35 inverse assumption (Java typed config → Go JSON-encoded ExtraAdapterInfo string) doesn't match thetradedesk's actual upstream Go pattern (Java typed config → Go raw string).

**Workaround in v6**: set `has_extra_info=False`. Emitted Go has no ExtraAdapterInfo handling at all. Functional divergence from upstream Go (which uses ExtraAdapterInfo as defaultEndpoint computation input), but for test config with empty ExtraAdapterInfo + supplySourceId on imp.ext (which thetradedesk's IT supplies), the runtime path doesn't need it.

**Severity**: HIGH for ports of typed-extraInfo Java adapters. Two distinct sub-cases:
1. **Rule 35 inverse, JSON-encoded shape** (e.g., adapters whose Go side actually uses `json.Unmarshal(cfg.ExtraAdapterInfo, &typedStruct)` — none in 5-pair batch): template's existing branch is correct; operator needs to fill the struct body from `spec.spring_config.configuration_properties_class.extra_fields[]` enumeration.
2. **Plain-string shape** (thetradedesk-style — Go uses ExtraAdapterInfo as a raw string for regex/template input): template's existing branch is WRONG. Need a new branch (`ctx.extra_info_kind: "raw-string"`) that emits a `string` field + regex validation + default-endpoint precomputation.

**Affected pairs in 5-pair MVP batch**: thetradedesk (only — adverxo, kobler, vungle, aax don't have typed extra-info).
**Affected pairs in full corpus**: thetradedesk + any other adapter with typed `extra-info.X` Spring config. Conservative estimate 2-3 in corpus.

**Recommended action**: add `ctx.extra_info_kind: "json-encoded" | "raw-string" | None` to the renderer schema. Default None matches `has_extra_info=False`. `json-encoded` matches today's behavior (operator fills struct). `raw-string` emits a new branch that includes:
- Adapter struct gets `defaultEndpoint string` field
- Builder validates `cfg.ExtraAdapterInfo` against `ctx.extra_info_validation_regex` (operator-supplied)
- Builder pre-computes defaultEndpoint via macros.ResolveMacros (when endpoint_resolution_kind=template-macro/multi-token)

This finding pairs with F-new-2: solving the multi-token endpoint branch fully also solves the raw-string ExtraAdapterInfo handling. Land them together.
