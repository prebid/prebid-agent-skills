### NEW: F-new-27 — multi-token-substitution endpoint TODO stub (HIGH; 2/16 corpus est.)

**Symptom**: Template's `resolveEndpoint` enum supports only `static` + `dev-prod-toggle`; everything else (including `multi-token-substitution`) emits a TODO comment + returns `a.endpoint` unmodified:

```go
func (a *adapter) resolveEndpoint(request *openrtb2.BidRequest) string {
    // TODO[port-java2go]: endpoint_resolution_kind=multi-token-substitution
    // requires per-bidder customization (Rule 11/12/14).
    return a.endpoint
}
```

**Functional consequence**: Emitted Go does NOT substitute `{{adUnitId}}` and `{{auth}}` tokens. Upstream Go adverxo.go uses:
1. `text/template` parsed in Builder (line 27).
2. `macros.EndpointTemplateParams{AdUnit: ..., TokenID: ...}` per-imp.
3. `macros.ResolveMacros(adapter.endpointTemplate, endpointParams)` to substitute tokens.

Operator hand-fill required for production fidelity. The canary worked because `TEST_ENDPOINT = "https://test.example.com/bid"` has no tokens to substitute (no `{{adUnitId}}` placeholder in the test endpoint).

**Captured**: in port-report.json::human_todos[]. Operator must:
1. Add `endpointTemplate *template.Template` field to `adapter` struct.
2. Parse config.Endpoint via `template.New(...).Parse(...)` in Builder.
3. Build a `buildEndpointURL(params *openrtb_ext.ImpExtAdverxo) (string, error)` helper using `macros.ResolveMacros`.
4. Replace `a.resolveEndpoint(&perImp)` with `a.buildEndpointURL(adverxoExt)` in MakeRequests per-imp loop.

**Severity**: HIGH. Either (a) extend template's resolveEndpoint enum with `multi-token-substitution` branch supporting `ctx.endpoint_token_set` schema (e.g. `[{token: "AdUnit", source_expr: "ext.AdUnitId"}, {token: "TokenID", source_expr: "ext.Auth"}]`), or (b) leave as TODO and operator hand-fills.

**Affected pairs in 5-pair MVP batch**: adverxo (only).
**Affected pairs in full corpus**: adverxo + any other multi-token adapter. F-new-26 (canary v4) flagged the related `query-parameter-augmentation` for aax — the two share a structural concern (both need URL augmentation/substitution helpers).

**Recommended action**: option (a) for thetradedesk-prep — thetradedesk per audit also uses URL augmentation (region-specific endpoint). Landing the multi-token branch for adverxo also supports thetradedesk-style patterns.

### NEW: F-new-28 — Cross-language ImpExt vs ExtImp naming asymmetry (MEDIUM; 2-3/16 corpus est.)

**Symptom**: Java declares `ExtImpAdverxo` (newer canonical form, used in modern Java adapters); Go upstream declares `ImpExtAdverxo` (legacy `ImpExt*` form). Go-side spec quirks[].legacy-impext-naming flags this as INFO-level. Template hardcodes `ExtImp{class_root}` in:
- `parseImpExt` return type: `func parseImpExt(imp *openrtb2.Imp) (*openrtb_ext.ExtImp{X}, error)`
- `parseImpExt` body: `var ext openrtb_ext.ExtImp{X}`

If the renderer doesn't hand-fill, the emitted code references non-existent `ExtImpAdverxo` and gate 1 fails with `undefined: openrtb_ext.ExtImpAdverxo`.

**Resolution in v5**: post-render `string.replace("ExtImpAdverxo", "ImpExtAdverxo")` in the renderer (5 occurrences in adverxo.go). Captured as F-new-28 in this doc + as quirk in port-report.

**Cross-language port consequence**: Java→Go porter must detect when target Go uses `ImpExt*` legacy naming and flip the template's class-root prefix. Java side has no `ImpExt*` ambiguity (always uses `ExtImp*`).

**Affected pairs in 5-pair batch**: adverxo (only).
**Affected pairs in full corpus**: any adapter with legacy `ImpExt*` naming on the Go side. Per audit, several of the older Go adapters use this form (count not enumerated; conservative estimate 2-4 in corpus).

**Severity**: MEDIUM (mechanical adjustment per pair via 1-line renderer fix). Could be promoted to a `ctx.imp_ext_legacy_naming` template flag that flips the generated `ExtImp{X}` → `ImpExt{X}`. Estimated effort: 6-line template addition.

**Recommended action**: option (b) for now (renderer hand-fill); promote to template flag in Phase 3 once 2-3 adapters surface the pattern.

### NEW: F-new-29 — Bid post-processing macros not template-emitted (LOW for this canary; HIGH corpus-wide for ADR-007 F4 master sample bidders)

**Symptom**: Upstream Go adverxo.go MakeBids calls `resolveMacros(&bid)` at line 122 to replace `${AUCTION_PRICE}` in `bid.AdM` with `strconv.FormatFloat(bid.Price, 'f', -1, 64)`. Template-emitted MakeBids does NOT do this — just unmarshal + by-mtype + append to TypedBids.

**Why didn't this fail gate 2?** IT bid-response.bid[0].adm = `<script>Ad markup with 1.23</script>` — already contains the literal `1.23` (substituted by adverxo's bidder before sending the bid back). The `${AUCTION_PRICE}` literal is NOT in the IT bid.adm, so the absence of `resolveMacros` doesn't change anything in the canary fixtures.

For real upstream traffic where `bid.AdM` contains literal `${AUCTION_PRICE}`, the emitted Go would forward the macro unsubstituted — operator hand-fills.

**Captured**: in port-report.json::human_todos[]. Operator must add a `resolveMacros` helper:

```go
func resolveMacros(bid *openrtb2.Bid) {
    if bid != nil {
        price := strconv.FormatFloat(bid.Price, 'f', -1, 64)
        bid.AdM = strings.Replace(bid.AdM, "${AUCTION_PRICE}", price, -1)
    }
}
```

**Severity**: LOW for this canary (IT happy-path doesn't exercise it). HIGH corpus-wide if templated for ADR-007 F4 bidders (audit lists adverxo, beachfront, others as having bid-post-processing-macro quirks).

**Affected pairs in 5-pair batch**: adverxo (only).
**Affected pairs in full corpus**: adverxo + others tagged `bid-post-processing-macro` in spec quirks. Audit suggests 3-5 pairs.

**Recommended action**: extend bidder.go.j2 with a `ctx.bid_post_processing` schema (kinds: `auction-price-macro`, `nurl-macro`, etc.). Estimated effort: 12-line template addition.
