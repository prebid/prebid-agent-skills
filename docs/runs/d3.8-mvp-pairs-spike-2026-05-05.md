### Audit-vs-golden divergence flagged

**thetradedesk row 232 of audit table**: audit shows `spring_extras: 0` (extra_fields count). But `prebid-server-java/read/test-fixtures/thetradedesk.golden.spec.yaml` shows:
- `spring_config.configuration_properties_class: TheTradeDeskConfigurationProperties` (NOT null)
- `spring_config.bidder_creator_lambda: "config -> new TheTradeDeskBidder(config.getEndpoint(), mapper, config.getExtraInfo().getSupplyId())"`

The Java config class file (`src/main/java/org/prebid/server/spring/config/bidder/TheTradeDeskConfiguration.java`) confirms: a private inner `TheTradeDeskConfigurationProperties extends BidderConfigurationProperties` carries an `ExtraInfo extraInfo` containing `String supplyId`.

The audit's `extra_fields` count uses an absent top-level `spring_config.configuration_properties_class.extra_fields[]` array. The thetradedesk spec doesn't enumerate that array — but the Java class IS a typed config subclass with a real extra field. **Severity: documentation gap.** Recommendation: either (a) update the spec to populate `extra_fields[]` (drift surfaced by canary) or (b) update audit script to also detect `bidder_creator_lambda` patterns mentioning `getExtraInfo()`.

For the canary itself: thetradedesk has `builder.extra_adapter_info_used: true` on the Go side. The current template's `{% if ctx.has_extra_info %}` branch will fire (Rule 35 inverse should hand-emit `extraInfo struct{ SupplyId string }`). The current template body has `// TODO[port-java2go]: operator fills fields ...` which means thetradedesk operator must hand-fill — same as kobler/beachfront/appnexus.

## Net-new findings (frequency-weighted; not yet in F-new-1..F-new-13)

These were latent in the audit corpus but not yet enumerated as findings; this spike confirms each will surface in 1+ canaries.

### F-new-14 — Per-status branching for `legacy-raw-go` (HIGH frequency: 2/5 in this batch, ~3/16 corpus)

**Symptom prediction**: For aax (Go: `legacy-raw-go`) the upstream adapter has THREE branches: 204 → return nil; 400 → BadInput; other-non-200 → BadServerResponse. Current template `legacy-raw-go` branch only emits two: 204 → return nil; non-200 → generic `unexpected status code`. The template will compile-clean but the EMITTED Go is functionally wrong (no BadInput vs BadServerResponse split).

**Affected pairs in 5-pair batch**: aax (3-branch); adverxo (2-branch — happens to match template). Combined frequency in 5-pair batch: 1 functional mismatch.

**Affected pairs in full N=16 corpus**: aax + beachfront + limelightDigital (all `legacy-raw-go` Java side; need verification per-pair what status-code branching pattern they use).

**Root cause**: Template's `legacy-raw-go` branch is a single 2-status case. Real `legacy-raw-go` adapters use ad-hoc branching that varies per-bidder.

**Fix recommendation**: Add a `ctx.legacy_raw_status_handlers: list[{status_code, error_kind}]` schema field; emit branch list in order. Spec needs to expose this.

**Severity**: HIGH (every Java→Go port of a legacy-raw-go adapter ships incorrect error semantics).

### F-new-15 — Site/App synthesis & replace-with-app-synthesis entity strategy (HIGH frequency: 1/5 in batch, ~6% in corpus today; likely 10–20% as more Liftoff/MMP-style bidders land)

**Symptom prediction**: vungle's spec has `mutation.entity_strategies: { Site: replace-with-app-synthesis, App: synthesize-app-replacement }`. Template body has NO branch consuming entity_strategies for Site/App. The emitted Go's MakeRequests will not synthesize the App from `bidderImpExt.PubAppStoreID`, will not nil out Site, will not set `imp.TagID = bidderImpExt.PlacementRefID`, will not set `bidderImpExt.BidToken = User.BuyerUID`, and will not re-marshal imp.Ext with the bidder slot embedded under `vungle` key.

**Affected pairs in 5-pair batch**: vungle.

**Affected pairs in full corpus**: vungle (only). Plus future Liftoff/MMP-style bidders.

**Root cause**: F7 (Device/User sanitization) mostly applies to "rezero PII fields" patterns; Site/App-synthesis is a different pattern (structural rewrite). Template must consume entity_strategies for Site/App in addition to Device/User.

**Fix recommendation**: Treat Site/App `replace-with-app-synthesis` and `synthesize-app-replacement` as NEW template branches that emit a per-bidder hand-fill TODO (or, per-pattern, a templated synthesis function) — the structure is too bidder-specific to fully template, but the framework can emit the scaffolding.

**Severity**: HIGH for vungle alone; MEDIUM corpus-wide.

### F-new-16 — Imp-mutation patterns: Site/App publisher rewrite, Banner.W/H from format[0], Imp.Ext nullification (HIGH frequency: 4/5 in batch)

**Symptom prediction**: 4 of 5 pairs (adkernelAdn, adverxo, vungle, thetradedesk) have `mutates_request: true` with `Imp: immutable-rebuild` on Java and `in-place` on Go. Template has NO body emission for Site/App/Banner mutation strategies. The emitted Go's MakeRequests will pass through the request unmodified — F-new-13's "passthrough body assumption" prediction was correct, but this spike confirms it's the DOMINANT case (4/5).

**Patterns observed**:
- adkernelAdn: `imp.Ext = nil` (strip after extraction); Site.Publisher = nil + Site.Domain = ""; App.Publisher = nil; Banner W/H from format[0] if missing.
- adverxo: `modifyImp` does currency conversion (handled by B2); also bid-post-processing `${AUCTION_PRICE}` macro replacement; native ADM unwrap (`getNativeAdm`).
- vungle: Imp.TagID = PlacementRefID; imp.Ext re-marshal with embedded vungle slot; Site→App synthesis.
- thetradedesk: Banner.W/H from format[0]; Site.Publisher.ID / App.Publisher.ID overwrite from extracted `publisherId`; `${AUCTION_PRICE}` macro substitution on bid.NURL/AdM/BURL.

**Root cause**: F-new-13 noted the issue at fixture level. Template-level fix is to emit MakeRequests body branches for the 5–6 most-common mutation patterns (or emit `// TODO[port-java2go]:` markers per-strategy with a reference upstream adapter).

**Fix recommendation**: Add `ctx.imp_mutations: list[strategy]` schema field. Per-strategy template branch emits an upstream-adapter-shaped helper. Affects ~50%+ of corpus.

**Severity**: HIGH (the dominant assumption-violation; appears in every non-trivial port).

### F-new-17 — Bid-post-processing `${AUCTION_PRICE}` macro substitution (MEDIUM frequency: 2/5 in batch, 2+ in corpus)

**Symptom prediction**: adverxo has `resolveMacros` substituting `${AUCTION_PRICE}` in `bid.AdM` after bid-type classification. thetradedesk has `resolveAuctionPriceMacros` doing the same on `bid.NURL`, `bid.AdM`, `bid.BURL`. Both are "ADR-007 F4 master sample" per the audit. Template MakeBids body has NO macro substitution emission.

**Affected pairs in 5-pair batch**: adverxo, thetradedesk.

**Affected pairs in full corpus**: at minimum these 2; ADR-007 F4 documents the pattern as a master sample, so likely more.

**Root cause**: Bid post-processing happens INSIDE the MakeBids per-bid loop, between bid-type-resolution and the `bidResponse.Bids = append(...)`. Template currently has no insertion point.

**Fix recommendation**: Add `ctx.bid_post_processors: list[step]` schema field with `kind: macro-substitution` and `target_fields: [AdM|BURL|NURL|...]`. Emit a `resolveAuctionPriceMacros` helper + per-bid loop call.

**Severity**: MEDIUM.

### F-new-18 — Native-ADM unwrap (LOW frequency: 1/5 in batch — adverxo only)

**Symptom prediction**: adverxo's MakeBids has a `getNativeAdm` post-processor that re-extracts `bid.adm.native` to `bid.adm` for native bids only. Conditional on `bidType == BidTypeNative`. Template has no such branch.

**Severity**: LOW — defer as `// TODO[port-java2go]:` per-bidder operator-fill.

### F-new-19 — Builder ExtraAdapterInfo regex validation (LOW frequency: 1/5 in batch — thetradedesk only)

**Symptom prediction**: thetradedesk's Builder validates `config.ExtraAdapterInfo` against regex `([a-z]+)$` — failing build if non-matching. Pure builder-side. Template's Builder body emits no regex validation.

**Severity**: LOW — operator-fill in `extraInfo struct{}` field handler.

### F-new-20 — Imp.Ext-strip-after-extraction (MEDIUM frequency: 1/5 in batch — adkernelAdn; observed elsewhere in corpus too per quirks)

**Symptom prediction**: adkernelAdn explicitly does `imp.Ext = nil` after extracting ExtImpAdkernelAdn (so the prebid wrapper is not forwarded to AdKernel's platform). This is a per-imp mutation that the template doesn't know about.

**Severity**: MEDIUM — spec exposes `quirks[]` containing `imp-ext-strip-post-extraction` taxon; template should consume this and emit `imp.Ext = nil` between parseImpExt and forward.

### F-new-21 — Empty-seatbid-shortcircuit unhandled in template (LOW; documentation gap, not a defect)

**Symptom prediction**: Java side carries `framework-default-plus-empty-seatbid-shortcircuit` for 4 of 5 pairs (all except adverxo which is plain `framework-default`). The template's Go-side `canonical-helpers` and `legacy-raw` branches DO check `IsResponseStatusCodeNoContent` (the 204 branch), which is the canonical Go "empty seatbid shortcircuit" idiom. So this is documentation-only — Java's framework-default-plus-shortcircuit IS already mapped to Go's canonical-helpers' 204-branch.

**Severity**: LOW — flag in port_engine docs, not a fix.

## Coverage gate prognosis

The Java IT 1-scenario bound caps coverage at the percentage of the upstream Go adapter's branches exercised by a single happy-path fixture. Kobler hit 65.4%. Predictions per pair:

| Pair | Approx upstream Go LOC | # branches | Predicted coverage with 1 IT scenario | Notes |
|---|---|---|---|---|
| aax | 150 lines (`aax.go`) | ~12 (3 status + 3 bid-ext-types + 3 imp-mediatypes + 2 typeCnt + ?) | **45–55%** (3-step bid type chain has many fallthrough branches; legacy-raw status-handler has 3 status branches that 1 IT can't exercise) |
| adkernelAdn | 290 lines (largest of batch) | ~20 (per-pubId grouping + compatBanner format[0] + nil seatbid checks) | **40–50%** (most branches outside happy path) |
| adverxo | 230 lines | ~15 (modifyImp + native-adm + bid post-processing macro + currency conv) | **45–55%** (currency conv + native-adm unreachable from 1 banner-only IT) |
| vungle | 150 lines | ~10 (Site/App synthesis branches + currency conv + re-marshal err) | **55–65%** |
| thetradedesk | 250 lines | ~15 (publisher branches + builder regex + macros) | **45–55%** |

**At what threshold can 80% be cleared?**

- With 1 Java IT scenario per pair: NONE of these 5 pairs will clear 80%.
- With 3-5 supplemental synthetic fixtures (status-204, status-400, no-response-body, malformed-body, currency-error, etc.): pairs 4/5 (vungle, aax, thetradedesk) likely clear 75–85%.
- With 8+ synthetic fixtures: all 5 likely clear 80%, but adkernelAdn and adverxo are corner-case-heavy and may need explicit fixtures for native-adm, per-pubId grouping, format[0]-fill, etc.

**Recommended decision** (matching kobler v2 recommendation): accept the structural gap. Either (a) lower D3.3 gate 3 threshold for Java→Go ports to 60% with `coverage_threshold_lowered_reason` field on port-report, or (b) emit synthetic supplemental fixtures (template the kobler-shape-agnostic ones — status-204, status-400, malformed-body — and let operator add per-bidder ones for currency conv / native-adm / etc.).
