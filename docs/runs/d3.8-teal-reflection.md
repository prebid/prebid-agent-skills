**Source**: canary 8 trace at [`docs/runs/d3.8-teal-canary-2026-05-05T-canary8-teal.md`](d3.8-teal-canary-2026-05-05T-canary8-teal.md).
**Audience**: future port-java2go SKILL maintainers + Phase F (reflection loop).
**Status**: forward-looking; the canary trace is the immutable historical record. This memo proposes actionable SKILL extensions and Phase F inputs.
**Author**: claude-code/opus-4-7 closing out the green-field port effort.

This memo identifies SKILL improvements that should land in a follow-up PR. The canary 8 emit landed 11 net-new findings (F-new-37 through F-new-47) with most fixed by hand-emit during the 5 polish iterations. This memo proposes how each finding should map to durable SKILL surface area changes (template branch / helper op / ctx schema field / validation rule), so future ports of similar-shape adapters land cleanly without the operator hand-fill teal needed.

## 1. SKILL extensions catalog

For each finding, this section proposes: helper function (signature + ctx schema slot if applicable); template branch (which template, what new ctx values, what output emission rules); validation rule (ctx warning surfaced by SKILL); estimated effort (small / medium / large); priority for v1.0.0 (required / recommended / nice-to-have); cross-language symmetry (does the inverse port-go2java need it too?).

Findings are grouped by SKILL surface area.

### 1a. `bidder.go.j2` template extensions

**F-new-37 — Per-imp imp.ext.prebid.storedrequest.id injection (M1)**
- **Helper**: extend `port_engine.simulate_makerequests_mutations` with new op kind `imp-ext-prebid-storedrequest-inject` taking `(imp, source_field_path)` where `source_field_path` is e.g. `"ext.bidder.placement"`. Returns mutated imp with `imp.ext.prebid.storedrequest.id` written when `source_field_path` is non-empty.
- **Template branch**: add `{% if ctx.imp_ext_storedrequest_inject %}` block to `bidder.go.j2`'s MakeRequests inner per-imp loop. Emits the `decodeJSONObject` + `decodeOrEmptyObject` pair + `jsonutil.Marshal` round-trip patch identical to teal's hand-emit at `teal.go:166-205`. ctx schema: `imp_ext_storedrequest_inject: {source_path: str}` where `source_path` is the dotted path under `imp.ext.bidder` (e.g., `placement` for teal).
- **Validation rule**: when `source_path` references a `*string` field in ExtImp, ctx-level lint that the field is pointer-typed AND validateImpExt rejects present-empty.
- **Effort**: medium (~80 lines template + 40 lines helper op + decodeJSONObject/decodeOrEmptyObject helper functions also need to land as Go-side reusable helpers since they're not openrtb_ext or jsonutil utilities yet).
- **Priority for v1.0.0**: recommended (3 of 8 canaries had related patterns — kobler imp.ext rewrap, thetradedesk SupplyId-into-imp, teal storedrequest-inject; argues for a batched "imp-ext-mutation" template family).
- **Cross-language symmetry**: yes — port-go2java needs the inverse (Go's `decodeJSONObject` + `jsonutil.Marshal` round-trip → Java `getOrCreate` chain). Land as a paired template extension.

**F-new-39 — Site/App Publisher.ID rewrite from first-imp ext.account (M2)**
- **Helper**: `_apply_site_publisher_rewrite` and `_apply_app_publisher_rewrite` ops already exist in `port_engine.simulate_makerequests_mutations` (per F-new-33 / canary v6). They were UN-WIRED in the renderer at canary 8 time. The helper extension is "wire the renderer to read `ctx.publisher_rewrite_id_from_ext` + `ctx.publisher_id_source` and auto-add to the simulator."
- **Template branch**: add `{% if ctx.publisher_rewrite_id_from_ext %}` block to `bidder.go.j2`'s MakeRequests post-per-imp body. Emits the `clonePublisherWithID` helper + `modifyBidRequest`'s site/app branches identical to teal's hand-emit at `teal.go:245-278`. ctx schema: `publisher_rewrite_id_from_ext: bool` + `publisher_id_source: str` (e.g., `"first_account"` to mean "first surviving imp's ext.bidder.account wins"; could be extended to `"per_imp"` later for adapters that rewrite per-imp differently).
- **Validation rule**: when site OR app appears in capabilities, but `publisher_rewrite_id_from_ext=False`, no warning. When `publisher_rewrite_id_from_ext=True` but neither site nor app is declared in capabilities, ctx-warning ("rewrite has no effect").
- **Effort**: medium (~50 lines template + 12 lines renderer wiring + 8 lines port_engine schema doc; helper ops already exist).
- **Priority for v1.0.0**: required (per canary v6 trace, this was the highest-priority unwired-helper case; teal makes 2 corpus pairs that need it without operator hand-fill).
- **Cross-language symmetry**: yes — port-go2java's inverse should consume the same ctx schema (Go's `clonePublisherWithID` → Java's `Optional.ofNullable(publisher).map(toBuilder).orElseGet(builder)` chain).

**F-new-40 — request.ext.bids stamp via FlexibleExtension property add (M3)**
- **Helper**: new op kind `request-ext-field-stamp` in `port_engine.simulate_makerequests_mutations` taking `(field_name: str, value: dict)`. Returns request with `request.ext.{field_name} = value` written; preserves all other top-level keys; treats absent / `null` ext as fresh empty.
- **Template branch**: add `{% if ctx.request_ext_field_stamp %}` block to `bidder.go.j2`'s MakeRequests post-per-imp body. Emits the `mergeBidsPBSFlag`-equivalent helper (with `decodeJSONObject` for null tolerance + `jsonutil.Marshal` re-serialization) identical to teal's hand-emit at `teal.go:280-292`. ctx schema: `request_ext_field_stamp: list[{field: str, value: dict}]` (list because some adapters might stamp multiple fields; teal stamps just one). Field name templated from `field`; value JSON-literal from `value`.
- **Validation rule**: lint that `value` is a JSON-encodable dict (no callables, no `set`, no `bytes`).
- **Effort**: small (~30 lines template + 20 lines helper op).
- **Priority for v1.0.0**: nice-to-have (only 1 of 8 canaries had this pattern; teal is the master sample).
- **Cross-language symmetry**: yes — port-go2java's inverse should emit Java's `ExtRequest.addProperty(field, valueNode)` chain.

**F-new-41 — `bidder.go.j2` emits duplicate `return openrtb_ext.BidTypeBanner` (template H3 gating bug; regression test)**
- **Helper**: none (this is a template fix).
- **Template branch**: in `bidder.go.j2`'s `imp-mediatype-introspection` branch, audit the H3 gating — the inner switch/case emits `return openrtb_ext.BidTypeBanner` for the matching-imp-with-banner path; the function tail emits `return openrtb_ext.BidTypeBanner` as the unmatched-loop default. The switch/case `case` for banner should emit `BidTypeBanner` and exit the switch via `return` — only ONE return-statement of `BidTypeBanner` should land. Hand-fix by removing the inner-switch return for the banner case (flow through to tail) OR by removing the tail return when imp-mediatype-introspection's hardcoded fallback kind is `banner` (tautological).
- **Validation rule**: SKILL test suite should add a regression test that renders `bidder.go.j2` with `bid_type_resolution=imp-mediatype-introspection` + `hardcoded_fallback_value=banner` and asserts the emitted Go has exactly ONE `return openrtb_ext.BidTypeBanner` statement (not two).
- **Effort**: small (~5 lines template fix + 30 lines regression test).
- **Priority for v1.0.0**: required (literal correctness bug, even if currently cosmetic — prevents future SKILL-emitted code from looking sloppy and avoids reviewer churn).
- **Cross-language symmetry**: no — Java side has no equivalent template duplicate-return pattern.

**F-new-42 — `bidder.go.j2` emits inverted mediatype priority (Java teal-specific vs Go default)**
- **Helper**: none (this is a template + ctx schema fix).
- **Template branch**: `bidder.go.j2`'s `imp-mediatype-introspection` branch currently hardcodes the Go-canonical priority `video > native > audio > banner` in the switch order. Add ctx schema `imp_mediatype_priority: list[str]` defaulting to `["video", "native", "audio", "banner"]`. Template iterates this list to emit the switch order. Teal would pass `["banner", "video", "audio", "native"]`.
- **Validation rule**: lint that the list is a permutation of `[banner, video, audio, native]` exactly (no missing types, no duplicates, no extras).
- **Effort**: small (~10 lines template + 5 lines ctx schema doc).
- **Priority for v1.0.0**: recommended (only 1 of 8 canaries needs the override, but it's a hand-fix-or-fail flagpole — without it any future Java-priority-different adapter requires operator hand-edit).
- **Cross-language symmetry**: yes — port-go2java should accept the same ctx schema for the inverse Java emit.

### 1b. `bidder-info.yaml.j2` template extensions

**F-new-43 — userSync block one-line vs multi-line YAML emit**
- **Helper**: none (template fix).
- **Template branch**: `bidder-info.yaml.j2`'s userSync block currently uses `{{ user_sync | tojson | safe }}` or similar collapsed form. Replace with explicit multi-line YAML emit:
  ```
  userSync:
    iframe:
      url: "{{ user_sync.iframe.url }}"
      userMacro: "{{ user_sync.iframe.userMacro | default('') }}"
  ```
  Rule: emit literal `&` (not `&`) for query-string ampersands; emit `{{.GDPR}}`, `{{.GDPRConsent}}`, etc. as Go-template-dot-syntax — DO NOT escape these (the Go side renders them at runtime via `macros.ResolveMacros`).
- **Validation rule**: lint that ctx.user_sync's URL fields have all 6 expected privacy macros for v3 spec (`{{.GDPR}}`, `{{.GDPRConsent}}`, `{{.USPrivacy}}`, `{{.GPP}}`, `{{.GPPSID}}`, `{{.RedirectURL}}`).
- **Effort**: small (~15 lines template fix).
- **Priority for v1.0.0**: required (every userSync-emitting pair benefits; cosmetic but reviewer-confusing).
- **Cross-language symmetry**: no — Java side's userSync YAML uses kebab-case not camelCase; the existing port-java2go renderer kebab→camel transform already handles the asymmetry.

**F-new-44 — `bidder-info.yaml.j2` misses `ortb.version` + `multiformat-supported` + `gpp-supported`**
- **Helper**: none (ctx schema fix).
- **Template branch**: add three ctx schema slots:
  - `openrtb_version: str | None` (e.g., `"2.6"`)
  - `openrtb_multiformat_supported: bool` (default False)
  - `openrtb_gpp_supported: bool` (default False)
  Template emits `openrtb:` block when any of the three are set:
  ```
  openrtb:
    version: "2.6"
    multiformat-supported: true
    gpp-supported: true
  ```
- **Validation rule**: when `openrtb_gpp_supported=True` but ctx.user_sync URL lacks `{{.GPP}}` macro, ctx-warning ("declared GPP support but URL doesn't carry GPP macro"). And vice versa.
- **Effort**: small (~25 lines template + 8 lines ctx schema doc).
- **Priority for v1.0.0**: recommended (most adapters declare ortb.version; gpp-supported is gaining adoption corpus-wide).
- **Cross-language symmetry**: no asymmetry — fields are present on both Java + Go yaml schemas.

### 1c. `port_engine.py` helper additions (especially `simulate_makerequests_mutations` new op kinds)

**F-new-37 helper op `imp-ext-prebid-storedrequest-inject`**: see §1a F-new-37.

**F-new-39 wiring of existing helper ops**: see §1a F-new-39.

**F-new-40 helper op `request-ext-field-stamp`**: see §1a F-new-40.

**F-new-45 — Nil-map panic guard helper**: add `_decode_object_with_non_nil_postcondition` Python-side documentation note that any helper op consuming `imp.ext` or `request.ext` MUST guard against JSON literal `null` and return a fresh empty object (not nil) on failure. The Go-side equivalent (`decodeJSONObject` with non-nil-on-error invariant) is included in any template branch that emits ext-mutation code (F-new-37 + F-new-40 are the two affected template branches). Effort: small (~20 lines doc + cross-reference). Priority: required (real-bug guard; would otherwise propagate to any future adapter using F-new-37 or F-new-40 templates).

**F-new-38 — Pointer-typed Placement schema lint**: ImpExt struct emit (currently in `port-java2go/templates/imp-ext-pojo.go.j2`) currently emits non-pointer Go fields for required Java fields and optional Go fields with `omitempty` for optional Java fields. Add a third bucket: optional Java fields where the Java side rejects present-empty (i.e., `if (placement != null && StringUtils.isBlank(placement)) throw`). For these, emit `*string` + `omitempty`. Ctx schema: per-field flag `optional_with_present_empty_rejection: bool` defaulting False. When True, emit pointer.
- **Validation rule**: lint that any ImpExt field with `optional_with_present_empty_rejection=True` has a corresponding `validateImpExt`-like check in MakeRequests (i.e., the SKILL-emitted code actually USES the pointer to detect present-empty).
- **Effort**: small (~10 lines template + 5 lines schema doc).
- **Priority for v1.0.0**: recommended.
- **Cross-language symmetry**: yes (Java side already correctly distinguishes via `placement != null && isBlank`).

### 2c. What was DISCOVERED by tests-we-wrote

The headline iter-quality observation: **tests we wrote ourselves caught a real fidelity bug the SKILL would have shipped silently.**

- **F-new-45 — nil-map panic on JSON `null` input**: discovered by `FuzzMergeBidsPBSFlag` and `FuzzModifyImp` in iter 2. The SKILL-emitted Go code (had it landed) would have shipped a Java-fidelity-divergent crash on adversarial inputs that Java tolerates cleanly. Adding test depth — fuzz harnesses specifically — was the only thing that surfaced this.

The implication: **the SKILL should ship fuzz harnesses by default** for any template branch that emits ext-mutation code (F-new-37, F-new-40) AND any other branch where adversarial JSON inputs (null / non-object / deeply-nested / unicode) could produce a runtime panic. A template-emitted `Fuzz*` harness with a curated seed corpus including null / empty / large / unicode-heavy inputs would have surfaced F-new-45 at canary v1 instead of canary v8.

Additional tests-discovered findings (non-SKILL-defect but corpus-improving):

- BR-02 (NBSP whitespace divergence Java vs Go) — discovered by Unicode-input fuzz seeds AND by the iter-3 isBlank Unicode test set; documented in doc.go cross-language fidelity surface.
- BR-03 (JSON map-key ordering divergence Java Jackson vs Go json-iter) — discovered by reading both encoders' source after iter-3 hand-test of `existing-request-ext.json` fixture; documented.

## 3. Phase F (reflection loop) inputs

Specific signals canary 8 surfaces that Phase F's reflection loop would consume. Phase F iterates: review canary trace + reflection memo → identify cross-canary patterns → extract durable improvements → land in SKILL.

### 3a. Cross-canary pattern: per-imp ext mutation

3 of 8 canaries (kobler, thetradedesk, teal) had per-imp `imp.ext` mutations the SKILL didn't emit:
- kobler: imp.ext rewrap with slot (F-new-15)
- thetradedesk: SupplyId + DfpAdUnit + storedrequest in imp.ext rewrap
- teal: per-imp prebid.storedrequest.id inject (F-new-37)

Argues for **a batched ext-mutation-helpers family** rather than three ad-hoc per-canary template branches. Phase F should consider:
- Defining a `ctx.imp_ext_mutations: list[{op: str, args: dict}]` schema instead of N booleans.
- Op kinds: `inject_field`, `rewrap_with_slot`, `strip_after_extraction`, `set_to_nil`, `merge_object`. Per-op args.
- Helper-side: a single Go-side `applyImpExtMutations(imp, ops)` function that the template invokes; each op kind has a Go implementation.

This is a larger surface change but reduces N+1 template branches to one branch + N op definitions. Estimated effort: large (~200 lines template + 150 lines port_engine). Priority: recommended (corpus-wide value beyond just teal).

### 3b. Template-bug pattern: F-new-41 dup return

F-new-41 (duplicate `return BidTypeBanner` from `imp-mediatype-introspection`) was in canary 8 ONLY among 8 canaries. The hardcoded-fallback branch went unexercised in canaries 1-7 because:
- canaries 1-7 used different `bid_type_resolution` kinds (`by-bid-mtype`, `method-chain-fallback`, `by-bid-ext-typed-field`).
- the only canary that DID use `imp-mediatype-introspection` (teal) is the canary that surfaced it.

Suggests **targeted regression test in port-java2go test suite** for every (`bid_type_resolution`, `fallback_action`) tuple. Each tuple should render to a syntactically-correct + semantically-correct getBidType function, asserted via `gofmt -e` AND a structural Go AST check that the function has the expected number of `return` statements (not a duplicate). Estimated effort: medium (~120 lines test + 6-10 fixtures). Priority: required (would have caught F-new-41 at SKILL-build time, not at canary 8).

### 3c. Operator-time signal: above-and-beyond mode is real work

Canary 8 took 5 polish iterations vs the 1-2 retry rounds of canaries 3-7. Wall-clock estimate from `plan.md §6` subagent dispatch table: 12-14 hours of subagent work + main thread coordination. Actual was higher — Phase E final verification (SA-7 + SA-8) added another ~3 hours; iter 5 review-skills + beyond-review SA-5+6 added another ~2 hours.

Net: above-and-beyond mode ≈ 4-5x the time cost of a "pass D3.3 gates and call it done" canary. The SKILL is currently optimized for the latter (operator can take a SKILL-emitted port and finalize for merge in 1-2 hours of hand-fill — see canary v7 trace lines 379-384). For above-and-beyond mode, the SKILL emits ~70% of the production-quality artifact and the operator polishes the remaining 30% (fidelity, idiom, docs, tests, fuzz, bench). The SKILL **could** emit the remaining 30% if these reflection-memo proposals land — particularly fuzz harnesses by default (§2c), pre-built doc.go scaffolds, and benchmark scaffolds.

**Phase F decision point**: should v1.0.0 promotion target above-and-beyond mode (SKILL emits ≥95% of production-quality) or canary mode (SKILL emits ≥70%, operator polishes 30%)? Canary 8's data argues for above-and-beyond — but at substantial template + helper investment cost.
