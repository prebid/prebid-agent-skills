## Iteration trace (3 retry rounds)

### Round 1 — first attempt with F-new-16 simulator

Renderer used `simulate_makerequests_mutations` with vungle-specific ops:
```python
mutations = [
    {"kind": "imp-ext-rewrap-with-bidder-slot", "slot_name": "vungle"},
    {"kind": "imp-tagid-from-ext", "ext_field_name": "placement_reference_id"},
]
```

Result: gate 2 FAIL — fixture body had `vungle` slot + `tagid: "placement_reference_id"`, but the template-emitted bidder.go is passthrough-style (no Site→App synthesis, no slot rewrap, no tagid set). Diff direction: expected had vungle slot + tagid, actual didn't.

This **confirmed F-new-15** at the template (not fixture) layer: the simulator helper accurately models upstream Go vungle, but the template emits a stock per-imp passthrough that lacks the vungle-specific mutations.

### Round 2 — reverted to passthrough fixture body

Removed simulator (`expected_request_body_simulator=None`). Body now equals mock_bid_request. Result: gate 2 closer — most fixtures matched. Remaining mismatch on `user.buyeruid: ""` (initially injected to avoid Go nil-deref of `requestCopy.User.BuyerUID`).

`openrtb2.User.BuyerUID` has `omitempty`, so the marshaled body has `user: {}` (empty object), not `user: {"buyeruid": ""}`. Updated fixture's mock_bid_request to inject `user: {}` directly.

### Round 3 — `no-response-body` supplemental mismatch

Gate 2 down to 1 failure: `vungletest/supplemental/no-response-body.json: MakeBids had wrong error count. Expected 0, got 1 ([expect { or n, but found ])`.

Root cause: the supplemental-fixture.json.j2 template at line 38-47 documents this exact gap — kobler-style adapters have an early nil-body short-circuit; canonical-go-helpers adapters (including vungle) fall through to `jsonutil.Unmarshal(nil_or_empty_body)` which errors. Captured as F-new-23 (template-doc-gap; not a defect). Removed `no-response-body` from vungle's supplemental set (left `status-204` / `status-400` / `status-404` / `malformed-body`).

Final gate 2 outcome after round 3: PASS clean.

### Confirmed by canary v3

#### F-new-15 — Site→App synthesis & vungle-slot imp.ext rewrap (HIGH for vungle)

**Predicted in spike**: yes (vungle-only finding).
**Confirmed**: yes — at the **template** layer.

**Symptom**: simulator-driven fixture body had vungle slot + tagid; template-emitted bidder.go does not produce these (no Site→App synthesis branch, no imp.ext rewrap branch, no imp.tagid assignment branch). Round 1 gate 2 FAIL diff was:

```
+    "vungle": { ... }    <- in fixture, missing in MakeRequests output
+    "tagid": "placement_reference_id"   <- in fixture, missing in actual imp
```

**Root cause**: `bidder.go.j2` has no schema-driven branches for `entity_strategies.Site = replace-with-app-synthesis`, `entity_strategies.App = synthesize-app-replacement`, or `imp_ext_unmarshal` with re-marshal/wrap requirements. Template emits stock per-imp passthrough.

**Resolution path**: ADR-007 F3 master-sample work (mediatype-context-rewrite-site-to-app). Two routes:
- (a) Operator hand-fill: emit vungle.go scaffold via template, then operator inserts the upstream-Go vungle MakeRequests body verbatim. Documented as `unresolved_translations[]` in port-report.
- (b) Template branches: add `ctx.imp_mutations` schema field (per spike F-new-16 recommendation) with kinds `app-synthesize-from-imp-ext` + `imp-ext-rewrap-with-slot`. Emit the upstream pattern shape per-bidder.

For canary v3 we accept the gap (passthrough body) and capture as a known-functional-divergence in port-report. Adapter compiles, tests pass, but the emitted Go does NOT functionally match upstream vungle (no app synthesis, no vungle-slot rewrap, no tagid set). For a real port submission, operator must hand-fill MakeRequests body.

**Severity**: HIGH for vungle alone; MEDIUM corpus-wide (vungle is the only known Site→App-synth bidder, but the imp-ext-rewrap pattern recurs in other unrelated bidders).

#### F-new-22 — Java IT auction-request lacks user object; Go adapter nil-derefs (NEW; HIGH for vungle, low frequency)

**Symptom**: Java IT `test-auction-vungle-request.json` has no `user` field. Java's `VungleBidder.modifyImpExt` at line 99 uses `ObjectUtil.getIfNotNull(bidRequest.getUser(), User::getBuyeruid)` → null-safe. Go's `vungle.go` at line 68 does `bidderImpExt.BidToken = requestCopy.User.BuyerUID` directly — **nil pointer deref panic** if User is nil.

**Cross-language fidelity gap**: Java is null-safe; Go panics. Either (a) upstream Go has a latent bug not exercised by upstream Go fixtures (which all populate `user.buyeruid`), or (b) prebid-server-go framework guarantees `request.User != nil` at adapter entry (unverified — the upstream Go vungle fixtures all set buyeruid, so the panic path is never tested).

**Resolution in v3**: renderer injects empty `user: {}` into mock_bid_request. The empty struct has `BuyerUID=""` which `omitempty` drops on marshal — wire-format body has `user: {}`.

**Affected pairs**: vungle (1/16). Possibly more if other adapters do `request.User.X` directly.

**Severity**: HIGH for fixture authoring (without the inject, the test panics); LOW for downstream Go correctness if framework-guaranteed.

**Recommended action**: surface in `port_engine.exemplary_fixture_assemble_java_to_go` as an opt-in `inject_empty_user_if_missing=True` parameter for adapters whose Go side does direct `User.X` reads. Alternatively, file an upstream Go issue noting the latent nil-deref in vungle.go.

#### F-new-23 — Supplemental no-response-body template assumes kobler-style nil-body short-circuit (LOW; documentation gap)

**Symptom**: `supplemental-fixture.json.j2` lines 38-47 already document this gap; canary v3 hit it. Template emits `expectedBidResponses: []` (no error), but vungle (canonical-go-helpers, no nil-body short-circuit) fails at `jsonutil.Unmarshal(nil)` with `expect { or n, but found `.

**Resolution in v3**: dropped `no-response-body` from vungle's supplemental set (4 supplementals retained: status-204/400/404/malformed-body). Reduces coverage marginally.

**Affected pairs**: any bidder with `http_status_handling=canonical-go-helpers` AND no kobler-style nil-body branch. Probably 50%+ of corpus.

**Severity**: LOW — already documented in supplemental-fixture.json.j2 prose; just needs a per-adapter selector in the renderer (skip `no-response-body` when http_status_kind != legacy-raw-with-nil-shortcircuit).

**Recommended action**: extend `supplemental-fixture.json.j2` (or its caller) with a `ctx.skip_no_response_body` flag, or compute it from `ctx.http_status_kind`. Single-line renderer fix.
