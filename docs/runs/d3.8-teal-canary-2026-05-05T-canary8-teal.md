## 1. Distinguishing characteristics

This canary differs from canaries 1-7 along six structural axes. The combined effect drove a 5-iteration polish budget vs the 1-2 iter typical for the 6-MVP corpus:

1. **Green-field port**: teal does NOT exist in `prebid-server-go` upstream (verified — `bidder-constant-table.yaml` jumps `taboola → tappx → teads → telaria → teqblaze`; no `teal`). Canaries 1-7 had a Go side to read alongside the Java; canary 8 is the first to emit Go where the only reference is Java itself.
2. **Namesake of the Teal flow**: the user mandated this canary as the "best teal port we can write", not "the cheapest port that passes gates." Quality bar from `plan.md §4` was set 10-20pp above corpus median on every measurable dimension.
3. **3 novel mutations not in the 6-MVP corpus**: M1 per-imp `imp.ext.prebid.storedrequest.id` injection; M2 first-imp account → Site/App.Publisher.ID propagation; M3 root `request.ext.bids = {pbs:1}` stamp via FlexibleExtension property add. None of canaries 1-7 exercised any of these patterns.
4. **5 polish iterations beyond the baseline** (vs 1-2 retry rounds for canaries 3-7). Each iteration targeted a specific quality dimension (fidelity / tests / idiom / docs / self-review).
5. **"Best in class" mandate from user** — canary 8 was instructed to exceed prebid-server-go corpus standards on every measurable dimension, not just clear D3.3 gates.
6. **Only canary to land beyond corpus-average quality** — canaries 1-7 met or slightly exceeded corpus baseline; canary 8 lands TOP QUARTILE on all 21 measured dimensions vs 3 hand-picked top-tier upstream Go adapters (openx, pubmatic, rubicon). Teal is the **only adapter** in the entire 267-adapter prebid-server-go corpus with fuzz tests, benchmarks, AND a doc.go file.

### F-new-38 — `ExtImpTeal.Placement` should be `*string` for absent-vs-present-empty fidelity

**Bucket**: helper + idiom.
**What it does**: Java distinguishes `placement == null` (absent → no validation, no M1) from `placement == ""` (present-but-blank → validation rejection). Go's `string` collapses these into one zero value; a `*string` field is required to preserve the trichotomy (nil / non-nil-empty / non-nil-non-empty).
**Triggers**: any Java-side optional-string field that must distinguish absent from present-empty.
**Status**: **fixed-this-canary by hand-emit**; SKILL emitted plain `string`. The canonical port-java2go pattern emits non-pointer for required + pointer for optional, but the SKILL doesn't currently emit pointer for "optional with present-empty rejection" — that's a third bucket the SKILL conflates with "optional + absent ok".
**Evidence**: `.tmp/teal-port/upstream/openrtb_ext/imp_teal.go:15`; test pins `TestMakeRequests_PlacementValidation` (3 sub-cases) and `TestMakeRequests_PlacementAbsent`.
**Severity**: LOW (per-canary; trivial 1-line fix). Corpus-wide LOW (rare pattern but specifically a SKILL gap on Go-side type system).

### F-new-45 — nil-map panic on JSON `null` input in `modifyImp` + `mergeBidsPBSFlag`

**Bucket**: fidelity (real bug).
**What it does**: When `imp.Ext` or `request.Ext` is the JSON literal `null` (or absent / empty), Go's `jsonutil.Unmarshal(b, &m)` where `m` is `map[string]json.RawMessage` leaves `m` nil. **Triggers**: any imp.ext or request.ext that is JSON `null` (rare in production but trivially adversarial; fuzz-discoverable).
**Status**: **fuzz-discovered (iter 2); fixed iter 3** by routing both call sites through `decodeJSONObject` which guarantees non-nil-on-error invariant.
**Evidence**: `.tmp/teal-port/upstream/adapters/teal/teal.go:223-235` (`decodeJSONObject` with non-nil-on-error postcondition); pin tests `TestMergeBidsPBSFlag_NullInputHandledAsEmpty`, `TestModifyImp_NullExtHandledAsEmpty`.
**Severity**: HIGH (per-canary — real fidelity bug + crash). Corpus-wide HIGH IF the SKILL ever emits direct `map[string]json.RawMessage` patches (currently only teal does, but F-new-37/40 templated would propagate the pattern; fix MUST land alongside the helper extension).

## 7. Cross-language divergences (intentional / stdlib-driven)

Four documented divergences. Match `doc.go:101-123`.

1. **Pointer-typed `Placement`** (`*string` in `ExtImpTeal`) — necessary because Go has no nullable strings; preserves the Java `placement == null` vs `placement == ""` trichotomy that drives both the M1 injection gate AND the validateImpExt rejection.
2. **URL validation lenience** — Java `HttpUtil.validateUrl` (Apache Commons) vs Go `net/url.ParseRequestURI` + scheme/host check. Edge cases like trailing dots in hostnames may differ; both reject `"invalid_url"` and require an absolute URL with scheme + host.
3. **Whitespace classification (NBSP and friends)** — Go's `unicode.IsSpace` returns true for U+00A0 NBSP, U+2007 FIGURE SPACE, U+202F NARROW NO-BREAK SPACE, U+1680 OGHAM SPACE; Java's `Character.isWhitespace` and Apache Commons `StringUtils.isBlank` return false for these. Inputs with NBSP-only account or placement therefore pass Java validation but FAIL Go validation. Strict-MORE-than-Java (Go rejects MORE; never accepts where Java rejects).
4. **JSON object key ordering** — Go's `jsonutil.Marshal` (`json-iterator` with `SortMapKeys: true`) sorts map keys alphabetically; Java's Jackson `ObjectNode` preserves insertion order. M1 and M3 emit objects via `map[string]json.RawMessage`, so byte-level wire output differs from Java even when the logical object is identical. Receivers compare logically (adapterstest uses jsondiff structural comparison), so this divergence is invisible in practice.

Two LOW-severity NOTE divergences from SA-7 fidelity audit §5 (Go strictly more defensive than Java; documented optionally):
- `imp.ext = {}` (object missing `bidder` key): Java NPEs on `null.getAccount()` (uncaught); Go returns clean `BadInput` with `"Error parsing imp.ext for impression {id}"`.
- `bidResponse.cur == null/""`: Java passes the null cur per-bid to BidderBid; Go defaults `bidderResponse.Currency` to `"USD"` via `NewBidderResponseWithBidsCapacity`.
